All four objects finally land on the client (post 16). So what does it do with
them? My test script kills the client before it draws a frame, but you don't need
a frame to find out. Let it run for a minute and listen to what it says.

## A controller with no body

I let it run seventy seconds and hooked everything the client sends. It never
sends a single update about a character it's driving. Instead it sends one small
message on the player controller's channel, and then this, over and over:

```
BUNCH ch=3 seq=0 open=0 close=0 rel=0 type=None dataBits=10   06 50 80 23 02
BUNCH ch=3 seq=0 open=0 close=0 rel=0 type=None dataBits=10   06 50 80 23 02
BUNCH ch=3 seq=0 open=0 close=0 rel=0 type=None dataBits=10   06 50 80 23 02
...
```

Fifteen thousand of them. About three hundred and twenty a second, byte for byte
identical. I looked at how tiny it was, thought "no body, nothing to report,
minimal movement update", and wrote it up as exactly that.

Then I actually decoded it. A movement update starts with a timestamp, which is a
decimal number, which is 32 bits on its own. This message has **ten bits** of
payload in total. It can't be a movement update. Ten bits is enough for one thing:
a field number and nothing else. A function call with no arguments.

## Now look up the number

Every replicated thing on a class, its synced properties and its remote functions,
gets a number. The number is what goes on the wire. Both ends build the same
numbered list from the same class definition, then just send numbers back and
forth. I built that list for the player controller weeks ago.

The two numbers the client sends: **33**, which my list says is
`ClientCommitMapChange`. And **71**, `Kismet_ClientPlaySound`.

Both start with `Client`. They're functions the *server* calls on the *client*.
"Play this sound." The client doesn't send those up the wire. It's like posting a
letter addressed to yourself and being surprised when it comes back.

So my list is wrong somewhere. And that same list labels every field in every
object my server sends. If it's wrong, I've been filling the client's objects with
garbage, and the client has been dutifully not crashing about it.

## Three sessions proving I was right

Here's where I got very thorough, and thoroughness turned out to be the problem.

**Check one.** I found the actual engine function that builds this list, by
comparing the tables of hidden function slots on each level of the class family
and spotting the one slot that changes at "full class". Decompiled it. It walks a
class's fields once, in the order they sit, and adds the networked ones. Exactly
what my code does. Clean alibi.

**Check two.** I rebuilt the expected list by hand from the readable decompiled
script, ninety fields across three classes. Matched my code exactly. Felt great for
about a minute. Then I went to write down *why* that check was independent, and it
isn't. The readable script is generated by the exact same function my numbering
code calls. I'd checked my code against a second copy of my code.

**Check three.** Fine. Properly independent this time: a reader that opens the
compiled file byte by byte with none of my usual tools. It got the very first field
wrong. Chasing that turned up an invisible block on every single field in the file,
an empty list of settings capped with the word `None`, that my usual tool had been
silently skipping for me the whole time. Account for it, re run: **all ninety,
byte for byte.**

So after three sessions: the list is right. The client really is sending functions
that only the server should send. Weird, but real.

## Sending the reply anyway

The client has a body with nobody driving it. The call that hands a character to
a player is `ClientRestart`, "this body is yours now". My server had never sent
it. So I built the code to send function calls, sent it, and watched the client
acknowledge it within two packets.

The flood didn't change a single bit. And the client did something new: it sent
back a **third** function that only makes sense going the other way. It had
appeared at the exact moment I made my call. Now I had three impossible messages
instead of two.

## The 45 second wall

Time to stop guessing from the wire and hook the moment the client decides to *run*
a function, so I'd see the real name instead of a table lookup. I built the hook,
ran it, and the client died partway through. I blamed my hook: it fires for every
single thing the game does, every frame, surely that's too slow. Trimmed it down a
thousandfold. Died again, same spot.

That made me stop and look at timestamps instead. I lined up five runs from that
day, three of which had no hook anywhere near this code. The gap between a dialog
box appearing and the client giving up:

45.01 seconds. 45.01. 45.02. 45.04. 45.03.

A fixed timer, there the whole time. I found a function in the script about a
broken data channel that disconnects the client, and wrote up a lovely precise
story tying the two together. Hold that thought.

## Asking the game what the numbers mean

First, an embarrassing one. My probe counts messages the client has swallowed,
and every run stopped at seven, which I'd read as "never got to number eight, the
important one". There is no number eight. I send seven. The important one is number
six, and it had arrived every single time. Great start to the day.

Then the real job. All three of my checks had one thing in common: they read the
**files**. None of them asked the **running game**. So I did.

Unreal keeps every name it knows in one big table in memory. I didn't know where
it lives, but name number zero is always the word `None`, so I searched the game's
memory for a list whose first entry points at `None`. Exactly one hit, holding
44,111 names. Then I asked: when the client got my `ClientRestart`, what did it
actually run?

`ServerCamera`.

A function for switching camera modes. I'd handed the client its body and it had
heard "could you change the camera please".

Then I hooked the spot where the client turns a field number into a field, and
dumped its entire list for all four objects. Put it next to mine.

![My list and the running game's list, side by side. Same names, opposite order: my field 0 is Physics, the game's field 0 is DrawScale. Lines cross in the middle. The only one that lines up is the middle field, because flipping a list doesn't move its middle.](mirror.svg)

Same length. Same names. Every class's chunk in precisely **reverse** order. Out of
563 numbers, 554 disagreed. The nine that agreed were each the middle entry of an
odd length chunk, which is right purely because the middle of a list doesn't move
when you flip it. Nine correct answers, all by accident.

Every check agreed with me because every check read the files, and the files agree
with themselves. Somewhere between the file and the running game, the game flips
the order. I checked my homework three times against the answer sheet I'd written.

And the mysteries all dissolved at once. The flood, under the real list, is
`ServerShortTimeout` and `ServerSetSpectatorLocation`: a client with no body,
floating around as a spectator, politely telling the server where it is.
Completely normal. The weird third message? The client receiving my accidental
`ServerCamera`, noticing it's a server function, and forwarding it to the server
like a confused receptionist. None of it was weird. I was reading it in a mirror.

## One line

Flip each class's list. Every self test passes, and my comparison script goes from
554 wrong to zero. Live run: `ClientRestart` runs. The camera points at the body.
The flood stops dead. And the game's log prints a line I've never seen from it:

```
GO player waiting
```

As for the 45 seconds: `BaseEngine.ini`, line 191, `ConnectionTimeout=45.0`. The
client hangs up 45 seconds after it last hears from the server, and after its first
burst, my server simply stops talking. The dialog box just happened to pop up at
about the moment my server went quiet. My beautiful four hundredths of a second,
five runs in a row, was a coincidence with a very precise number hung on it.

Next: teach my server to keep talking, and actually look at the screen.
